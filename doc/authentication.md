# Авторизация

## Поток запросов

1. JSON-вход `/api/auth/login` проверяет пароль через PasswordEncoder.
2. Ответ содержит accessToken и HttpOnly-cookie JR_ACCESS с тем же JWT.
3. GET страницы проверяет JWT; Thymeleaf передаёт токен в meta, auth.js забирает его
   в память и удаляет meta. jQuery и обычные POST-формы используют Bearer-заголовок.
4. Выход повышает USERS.TOKEN_VERSION, поэтому все ранее выданные JWT этого пользователя
   перестают работать. JWT также привязан к текущему хэшу пароля.

Роли не доверяются содержимому клиентского токена: берутся из актуального пользователя.
Чужой Origin, запрос изменения с одной cookie, неподписанный/просроченный JWT отвергаются.
Для HTTPS обязательно COOKIE_SECURE=true. Токен не хранится в localStorage и не передаётся
в query string. При XSS код того же origin всё равно может действовать от имени пользователя;
HttpOnly не заменяет экранирование пользовательского содержимого.

## Совместимость с серверными страницами

SessionCreationPolicy.STATELESS вместе с NullRequestCache отключает сессионный вход.
В используемой Spring Security 6.0.1 отдельное переопределение SecurityContextRepository
мешало внутренней настройке SessionManagementFilter и создавало JSESSIONID при реальном
HTTP-запросе. Поэтому такой override удалён; регрессия проверяется StatelessHttpTest
на настоящем embedded Tomcat, включая главную страницу, дерево и профиль.

OAuth не сохраняет provider access token в сессии. Временный state проверяется по
HttpOnly-cookie и одноразовой записи в ограниченном кэше. После callback выдаётся JWT.
Подтверждение почты и смена пароля тоже не требуют сессии исходного браузера.
Для незавершённых OAuth/почтовых операций перезапуск приложения означает повторный запрос ссылки.

Отсутствующие статические файлы сохраняют HTTP 404 и не очищают JWT-cookie.
ERROR-dispatch разрешён отдельно, чтобы повторная обработка ошибки без SecurityContext
не запускала перенаправление на вход. Обычные запросы к защищённым адресам по-прежнему
проходят проверку авторизации. Этот случай также проверяется реальным HTTP-тестом.

Модель redirect не получает authUser/accessToken: Spring иначе превращает строковые
поля модели в параметры URL. Уведомления профиля рендерятся в ответе POST, а изменения
пользователя передают только короткий код результата. Flash attributes удалены,
поскольку их стандартное хранилище создаёт HTTP-сессию. HTTP-тест проверяет также
сохранение обеих форм, ошибки валидации и смену пароля, включая отсутствие JWT в Location.
